# Part 3 — 分镜与视觉导演

本模块把已锁定剧本与 Part 2.5 产出的最终配音 / 正式对齐 SRT 转换为可执行的分镜与视觉导演方案。

---

## 1. Part 3 负责什么

Part 3 接收：
- 已锁定剧本；
- 已锁定机制 / 事实边界；
- Part 2.5 的最终配音音频；
- 与该音频真实对齐的正式 SRT / 必要停顿时间信息；
- 当前视觉风格与角色 / 世界约束。

Part 3 负责回答：

> **这一刻故事世界里发生什么？观众应该看什么？从哪里看？为什么要单独有这一张图？**

Part 3 负责：
- 戏剧层级与段落变化；
- 整集 / 段落视觉策略；
- Scene System 的故事用途与空间 / 状态规划；
- 视觉意图；
- Semantic Shot；
- Visual Beat；
- 景别、POV、构图与视觉重点；
- 画面之间的连续、对比、并列、隐喻、蒙太奇关系；
- 单帧注意力组织 / Frame Blueprint；
- 100% 锁定口播覆盖；
- 基于真实音频时间的视觉节奏映射；
- 分镜级 QA。

Part 3 不负责：
- 改写剧本事实或台词；
- 决定 TTS 声音、语速或最终语音时长；
- 重新切写正式 SRT 文本；
- 最终图片 prompt；
- 角色 / 场景 / 道具参考图绑定；
- 图片模型与执行参数；
- 最终图片文件与 Registry；
- 成片渲染。

最终配音与 SRT 对齐属于 Part 2.5；图片规划属于 Part 4 + Part 4.5；生图执行与后续视频合成属于下游模块。

### 长期视觉基线

Part 3 的长期视觉基线由 **3 张角色 Master + 1–2 张经确认的 Style Plate** 构成。

#### 角色 Master

- **主角**：[`MAIN_CHARACTER_MASTER.png`](assets/characters/MAIN_CHARACTER_MASTER.png)
- **男生朋友 / 舍友**：[`MALE_FRIEND_ROOMMATE_MASTER.png`](assets/characters/MALE_FRIEND_ROOMMATE_MASTER.png)
- **女生朋友 / 同事**：[`FEMALE_FRIEND_COLLEAGUE_MASTER.png`](assets/characters/FEMALE_FRIEND_COLLEAGUE_MASTER.png)

#### Style Plate

Style Plate 只锁定：
- 线条；
- 上色；
- 人物比例；
- 阴影与材质；
- 色彩关系；
- 人物与环境的整体完成度与视觉气质。

Style Plate 不定义：
- 具体场景；
- 桌椅、杯子、食物等具体道具；
- 窗景、昼夜或天气；
- 人物姿势 / 动作；
- 具体构图。

Style Plate 应尽量使用中性、弱剧情、弱场景的画面，避免让具体生活场景内容被误当成长期视觉事实。正式使用前必须是经确认的 Style Plate；具体文件在长期资产目录中登记。

规则：
- 三张角色图主要锁定长期角色身份、外形、比例与轮廓；基础服装作为默认参考，单集可因剧情合理变化；
- 男生配角默认是主角的朋友 / 舍友；
- 女生配角默认是主角的朋友 / 同事，不默认建立恋爱关系；
- 当前不设置长期固定场景、旧类比场景、长期 UI 或长期道具；
- 面馆、老板、食物、酒店、街道、具体 UI / 道具等均按单集故事需要产生；
- Part 3 必须尊重长期角色与 Style Plate 基线，但不负责为每个 Beat 选择具体执行参考图；具体绑定留给后续图片 / 资产模块。

## 2. 输入不能被导演偷偷改掉

Part 3 必须保留：
- 锁定口播文本与顺序；
- 核心机制与事实边界；
- 人物、事件、因果状态；
- 已发生 / 未发生的事实；
- 关键数量、关系、时间、天气和场景锚点；
- setup / reveal 的信息边界；
- Part 2 已确认的叙事视角入口。

禁止为了“好画”而：
- 把假设未来画成已经发生；
- 发明新人物、新行为、新结果；
- 改变故事因果；
- 把真实事件替换成抽象解释图；
- 用画面新增未经批准的可读事实。

如果剧本没有足够真实可视事件，不应由 Part 3 发明事件，应返回上游处理。

## 3. 当前正式工作结构

正式执行收敛为三层：

```text
锁定剧本 + 机制核心 + Part 2.5 最终配音 / 正式 SRT
→ 1. 整集 / 段落视觉策略
→ 2. Semantic Shot
→ 3. Visual Beat
→ Director Shotboard
```

当前三层包含：

- 整集 / 段落视觉策略先锁定主要视觉载体、Scene System、世界 / 空间状态、段落之间的视觉差异和重复风险；
- Semantic Shot 记录故事变化、主要视觉意图和导演级视觉策略；
- Visual Beat 记录具体完整静帧状态、单帧注意力组织和真实音频时间字段；
- 时间字段直接绑定 Part 2.5 的正式 SRT / 真实音频锚点。

层级边界：
- **Semantic Shot** 主要判断“故事为什么在这里进入新的阶段”；
- **Visual Beat** 主要判断“为了让观众看懂这次推进，需要哪些不同的完整画面”。

因此，一个 Semantic Shot 可以包含多个 Visual Beat；有意义的故事变化不等于每一张图都必须发生重大价值转折。

整体视觉规划必须发生在逐 Beat 设计之前；不能先把所有 Beat 拆完，再仅靠末端 QA 修复整集重复。

## 4. 第一硬门：这一刻故事世界里实际发生了什么

每个主要段落 / Visual Beat 在进入单帧设计前必须能回答：

> **这一刻观众看到的内容属于什么叙事事实？故事世界里实际发生 / 显现了什么？**

至少明确：
- 谁 / 什么是行动主体；
- 实际动作、状态或外部事件；
- 之前是什么状态；
- 之后是什么状态；
- 谁承受 / 看到后果；
- 观众必须读懂的意义；
- 该画面属于客观事件、已锁隐喻、主观脑补 / 假设，还是一般机制示范。

允许的四类画面必须分清授权边界：

1. **客观故事事件**：锁定故事中真实发生的行动、反应、空间变化、物件、真实 UI / 文件和后果；
2. **已锁隐喻世界**：Part 2 已建立并持续运转的比喻世界，可按既定规则推进，但不得临时为解释方便新增一套隐喻；
3. **主观脑补 / 假设 / 计划**：允许可视化，但必须让观众能辨认其主观 / 未证实属性，不能画成客观事实；
4. **一般机制示范**：只有上游机制已支持且不冒充本集个案证据时才允许；不能因为“机制通常如此”就声称主角这次具体事件必然由该原因造成。

对 **主观脑补 / 假设 / 计划**，不能只写“主观气氛”。Part 3 必须锁定可执行的主观视觉语法，至少说明：
- 现实锚点是什么；
- 从现实进入主观状态时，观众靠什么视觉差异识别；
- 主观画面中哪些内容只是人物想象 / 推测；
- 何时、如何回到客观现实。

这种区分必须由画面本身成立，不能主要依赖“脑补 / 假设”文字标签。不得用后台证据、因果箭头、流程图或解释卡，把未证实猜测伪装成客观事实。若一张图无法清楚承载该主观状态，可以重新拆分 Visual Beat。

例如：
- “我怀疑平台看出来我想订了”可以画成明确的主观脑补；
- 不能直接客观展示后台给主角贴“已上钩，涨价”标签；
- 匿名酒店客房从夜晚到清晨可以示范“房晚具有时效性”，但不能据此证明主角本次涨价就是因为这一间房昨晚没卖掉。

优先承载方式：
- 人物行为；
- 人物反应；
- 真实道具；
- 真实世界内 UI / 文件 / 消息 / 收据；
- 空间变化；
- 关系变化；
- 可观察的现实后果；
- 已授权且事实属性清楚的隐喻 / 主观 / 一般示范。

当前漫画叙事基线：

> **抽象解释图不能替代故事事件。**

禁止默认使用：
- 漂浮规则卡；
- 流程图；
- 抽象路径 / 箭头；
- 阈值板；
- 关系线；
- 分支图；
- 把手机 / AI 拟人成解释代理；
- 把口播比喻直接画成字面门、方向盘等解释符号；
- 把旁白文字可视化成 PPT。

真实设备或场景中本来存在的导航箭头、列表符号等不属于解释图禁令。

如果唯一答案是“这张图解释旁白”，先在 Part 3 重新找故事事件 / 已授权视觉承载；如果剧本本身没有可画事件或一般示范需要新增事实授权，返回 Part 2。

## 5. 戏剧层级（Semantic Shot 字段）

不再单独产出戏剧层级文档。设计 Semantic Shot 时记录对应的故事变化即可。

使用：
`Sequence → Scene → Beat`

- **Beat**：最小动作 / 反应 / 策略变化，不要求每个 Beat 都是重大价值转折。
- **Scene**：一串连续 Beat，产生可感知的故事 / 状态变化。
- **Sequence**：多个 Scene 形成更大的累积变化。

它只回答“故事发生了什么变化”，不决定景别、机位、构图和图片时长。

避免：
- 戏剧层级完全扁平；
- 只按句子 / SRT 条目机械切 Beat。

## 6. 整集 / 段落视觉策略

**这一节必须在逐张 Visual Beat 设计前完成。**

先确定：
- 主视觉发动方式；
- 可选次视觉发动方式；
- Scene System；
- 每个主要 Sequence / 段落的状态变化；
- 每段主要视觉载体；
- 人物实际做什么 / 承受什么；
- 世界有什么可见后果；
- 哪些精确信息必须由 UI / 文件 / 道具呈现；
- 与前后段落在哪些方面重复、在哪些方面必须产生有意义差异；
- 0–2 个有意义的视觉母题；
- 1–3 个主要视觉构成因素；
- 视觉强度、信息密度和节奏变化；
- 各 Sequence 的画面关系语法。

### Scene System：先规划故事用途，不先生产资产

Part 3 的 Scene System 负责在生图前写清：
- 本集需要哪些地点 / 功能区；
- 每个空间承担什么故事任务；
- 人物与关键对象的重要空间关系；
- 重要时间 / 天气 / 昼夜；
- 何时进入 / 离开；
- 哪些区域 / 对象会重复；
- 哪些状态必须稳定，哪些状态允许变化。

对会重复出现、且连续性影响故事理解的关键空间，Part 3 还要建立 **Scene Anchor**。Scene Anchor 至少锁定：
- 空间身份；
- 时间 / 昼夜 / 天气状态；
- 主要故事用途；
- 哪些 Sequence / Semantic Shot / Visual Beat 必须延续该空间；
- 何时允许离开、切换到新空间或 later event。

Scene Anchor 锁的是导演事实，不锁具体图片文件、asset ID 或 reference path；这些执行绑定由 Part 4 决定。

Scene System 不等于 Scene Master 图片库。

- 不恢复“必须先生成 4–8 张 Scene Master”；
- 不要求固定地点数量；
- 单地点故事允许成立；
- Part 4 再根据连续性风险决定是否需要 canonical 图、兼容旧图、本集早期 accepted frame 或 mini master。

判断 Scene System 是否合格，看的是**故事用途与状态关系是否清楚**，不是预生成了多少场景图。

### 现实行动 / 世界后果优先原则

当剧本本身已经提供人物行动、空间变化、关系变化或现实世界后果时，优先让它们承担正文，不要为了方便长期退化为 UI → reaction → UI → reaction。

但这不是比例配额：

- 精确价格、条件、订单状态等确实需要 UI 时就使用 UI；
- 调查 / 搜索 / 证据阅读题允许连续 insert；
- 不为了“减少 UI”强加新地点、配角或未发生动作；
- 不设置 Tableau 百分比或“每段必须一个现实场景”的硬门。

例如酒店题：
- “价格 600 → 750”适合 UI；
- “昨晚这间房的销售机会过了就消失”若上游已授权一般机制示范，更适合夜晚客房 → 清晨世界状态，而不是再画一页解释 UI。

### 发动方式与画面关系

支持的视觉发动方式包括：
- 行动 / 反应；
- 演化隐喻；
- 重复摩擦；
- 调查 / 发现；
- 关系对话；
- 过程变化；
- 对比；
- 物件驱动；
- 联想蒙太奇；
- 混合。

它们是配置，不是新的导演流程；采用新配置必须有故事理由，不因为列表存在就声称每种都已经独立验证。

画面关系可使用：
- 连续；
- 并列；
- 蒙太奇；
- 对比；
- 隐喻；
- 插入物主导；
- 澄清。

不要求所有段落都模拟连续电影空间。

### 在规划阶段检查重复

在拆 Beat 前先看主要段落是否已经出现：
- 长段只有坐着看手机；
- 连续相似 UI；
- 同一种 reaction；
- 每个 complication 都靠另一页屏幕解释；
- 场景名称虽不同，但人物任务和视觉载体其实没变。

重复若承担调查、累积、摩擦或喜剧任务，可以保留并让差异可见；无意义重复应在这里先改承载方式或返回剧本，而不是等所有图片都规划完后再靠末端 QA 补救。

不设置固定秒数、固定镜数、固定地点数或视觉类型配额。

## 7. 视觉意图（Semantic Shot / Visual Beat 字段）

不再单独产出 Visual Intention Map。每个 Semantic Shot 记录主要意图；Visual Beat 如有必要可局部覆盖。

每个有意义的单元先决定观众此刻最需要：
- 建立环境；
- 跟随行动；
- 读反应；
- 注意物件；
- 共享人物视角；
- 感受关系；
- 看见后果；
- 经历反转；
- 接住包袱 / 回报；
- 跟踪隐喻状态；
- 比较状态；
- 建立模式；
- 澄清机制。

**先决定意图，再选镜头。**

不能因为“这个镜头看起来好看 / 有变化”反过来寻找理由。

---

## 8. Semantic Shot

Semantic Shot 是一个连贯的导演级视觉策略，也是 Part 3 中承载主要故事推进的层。

建立新的 Semantic Shot 前，先确认：

> **这一段结束时，人物的处境、认知、关系、选择、策略或重要后果，是否发生了值得单独标记的有意义变化？**

仅出现新信息、新表情、新动作、新机位或新 UI 状态，不自动成立新的 Semantic Shot。关键转折必要时可以用“人物想得到什么 / 遇到什么阻力 / 原本预期什么 / 实际发生什么”辅助判断，但不新增强制字段。

以下变化仍可作为建立 Semantic Shot 的信号：
- 人物行动 / 策略发生有意义变化；
- 人物反应改变了下一步行动或故事体验；
- 观众获得改变理解的关键信息；
- 主要人物 / 物件的因果地位改变；
- POV 改变带来新的重要发现；
- 人物关系 / 空间站位改变了故事关系；
- 地点 / 世界状态改变并产生后果；
- 隐喻状态发生推进；
- 出现后果 / 反转 / 回报；
- 画面关系语法随故事阶段改变；
- 所需视觉强度随故事阶段改变。

每个 Semantic Shot 至少保留：
- 对应戏剧段落；
- 主要视觉意图；
- 镜头功能；
- 主体优先级；
- 站位 / 动作关系；
- 景别策略；
- POV 策略；
- 构图策略；
- 视线 / 注意力衔接；
- 必要的空间连续规则；
- 视觉强度；
- 画面关系；
- 当前视觉状态；
- 通过条件。

Semantic Shot 不必锁死每一张子图的具体 POV / 景别。

## 9. Visual Beat

关系：

`Semantic Shot → 1..N Visual Beats`

Visual Beat 是最接近“一张最终完整画面”的导演单元。

每个 Visual Beat 至少锁定：
- 对应口播范围；
- 本地视觉意图；
- 这一刻实际发生什么；
- **最终静帧停在哪个可见状态**；
- 实际景别；
- 实际 POV / 角度；
- POV 原因；
- 主要人物 / 物件状态；
- state_before / state_after；
- 主要焦点，可选第二焦点；
- 构图 / 注意力路径；
- 信息密度；
- 必要背景锚点与应压低内容；
- continuity preserve / frame delta；
- 必要 withheld information；
- 画面关系；
- 视觉强度；
- 基于正式 SRT 的时间线锚点与 cut / hold / handoff；
- 观众必须理解什么；
- acceptance criteria。

### 最终静帧状态

`state_before / state_after` 是因果上下文；最终画面状态明确“这一张完整图真正停在哪一刻”。

可例如：
- 准备动作；
- 动作中的关键瞬间；
- 动作完成后的结果；
- 等待；
- 读到信息；
- 反应；
- 世界状态已经改变后的可见结果。

不要把“打开页面 → 看到涨价 → 愣住”整段过程塞进一个 prompt。若“看到涨价”和“人物反应”都新增必要图像意义，可以拆成相邻 Beat；若只有结果重要，则只锁结果静帧。

只有当**图像级意义发生变化**时才拆新 Beat，例如：
- setup → action；
- action → result；
- cause → meaningful reaction；
- joke setup → landing；
- 关键物件 / UI 状态变化；
- 有意义的 POV discovery；
- 隐喻状态变化；
- 比较 A → B；
- 真正产生意义的蒙太奇累积；
- 视觉强度发生必要变化。

### 不拆的情况

以下本身不自动产生新 Beat：
- SRT 新增一条；
- 旁白多了一个分句；
- 连续列举几个词；
- 想让画面“多变一点”；
- 只有手指位置 / 轻微表情 / 微小构图差异改变；
- 一张完整图已经能承载相邻口播且不会损失新的动作、因果状态、关注点或 POV。

原则：

> **Beat 数量不是配额。**

Visual Beat 不要求每一张图都产生重大的处境 / 认知 / 价值变化。只要新增了观众需要看到的图像级意义，reaction、setup / reveal、因果证据、UI / 道具状态、必要 POV discovery、喜剧落点、动作结果等仍可独立成为 Visual Beat。

不使用固定平均秒数、固定图片数量或 SRT 条数作为 Beat 配额；优先保证 Beat economy。

---

## 10. Setup / Reveal / Reaction

当“先不让观众看到结果”本身有戏剧意义时，可以拆：
- setup；
- reveal；
- reaction。

要求：
- setup 不能提前泄露 payoff；
- reveal 必须真的新增信息；
- reaction 只有人物反应本身改变故事体验时才单独存在。

当故事结论依赖“前态 → 后态”的变化时，画面必须提供可见证据。必要时使用 `setup → matched reveal` / `before → after`，让观众能从画面本身识别变化。不是所有比较都必须拆成两张，但不能主要依赖“更高 / 稍贵 / 发生变化”等解释标签来证明变化。

不要为了模仿动画动作过程，把一个仍可由一张完整图表达的动作拆成大量微小状态。

---

## 11. POV：从戏剧功能选择

核心问题：

> **这一刻观众应该看主人公，还是和主人公一起看？**

### 旁观
适合：
- 表情；
- 身体语言；
- 犹豫；
- 行为改变；
- 人际 / 空间关系。

### 第一人称 POV
适合：
- 阅读；
- 发现证据；
- 看具体文字 / 状态；
- 对比信息；
- 从人物经验进入 UI / 文件。

### 第一人称手部
适合：
- 人物亲手写、点、拖、签、支付、移动；
- 这个手部动作本身制造后果。

### 越肩
适合同时保留：
- 人物对动作的所有权；
- 可读的目标 / 屏幕 / 物件。

### 客观插入
适合：
- 物件 / UI 本身就是因果证据；
- 不需要人物表情。

### 关系旁观
适合：
- 两个人之间的关系 / 对话 / 空间关系是重点。

第一人称口播不意味着所有画面必须第一人称。

每次 POV 变化必须有信息 / 故事理由，不能只为视觉变化。

每个 Beat 应记录 `pov_reason`。

---

## 12. 物理视角必须成立

POV 标签正确不代表画面物理成立。

涉及可读屏幕 / 文件 / 物件与人物时，必须检查：
- 摄像机在哪里；
- 屏幕 / 纸张朝向哪里；
- 人物看哪里；
- 观众实际能看到哪一面；
- 人物是否真的能看到自己被描述为正在看的内容。

典型错误：
- 屏幕正对观众，同时人物站在屏幕后方却像在阅读屏幕正面；
- 画面要求观众同时看到互相冲突的正反两面；
- 人物目光与因果物件不在可成立的空间关系中。

如果一张图不能同时承担“看人物反应”和“读屏幕证据”，拆成相邻的 reaction / discovery Beat，前提是两者都新增意义。

物理不可能时返回，不允许靠“生成模型大概能画”放行。

---

## 13. 景别与镜头选择

景别按信息需要选择：
- 远 / 全：地点、人物关系、尺度、全身动作、世界状态；
- 中：互动、手势、任务、操作物件；
- 近：重要反应、决定、潜台词；
- 插入：因果物件、UI、证据。

不为了“镜头语言丰富”随机改变景别。

镜头优先级遵循：
1. 情绪；
2. 故事；
3. 节奏；
4. 视线；
5. 二维画面；
6. 三维连续。

高层意义可以有理由牺牲低层连续性，但不能无理由破坏。

---

## 14. 单帧字段

核心问题仍然保留：

> **观众怎样在第一眼看到这一 Beat 最重要的东西？**

Visual Beat 可使用以下单帧字段：

### 常用单帧原型
- 人物反应；
- 人物行动；
- 双主体关系；
- 物件 / 证据插入；
- 世界状态；
- 双状态对比；
- matched setup / reveal。

### 焦点
- SINGLE：一个绝对主焦点，默认；
- DUAL：两个有关系的焦点；
- FIELD：多个元素共同形成一个整体模式。

FIELD 不能只是为了塞更多信息。

### 信息密度
- LOW；
- MEDIUM；
- HIGH_JUSTIFIED。

高密度必须有叙事理由。

构图、注意力、背景压低、continuity preserve、frame delta、withheld information、acceptance criteria 均记录在 Visual Beat 中。

---

## 15. 单帧注意力与背景经济

一张画面优先级：
1. 故事动作 / 反应；
2. 主体层级；
3. 空间关系；
4. 因果道具 / UI；
5. 风格装饰。

背景只保留：
- WORLD_ANCHOR：定位世界；
- STORY_PROP：推动事件；
- 必要的角色化细节。

普通装饰不能和主要动作竞争注意力。

“简化背景”不等于所有 Beat 都在同一张桌子前。

当地点、天气、进入 / 离开、人与人距离本身有故事意义时，应保留真实空间。

---

## 16. 机制画面的优先顺序

当需要让观众理解机制时，优先依次尝试：
1. 故事后果；
2. 人物行动 / 决定 / 交接；
3. 道具或世界规则真实变化；
4. 演化隐喻；
5. POV / 真实物件 / 真实 UI；
6. 蒙太奇 / 对比；
7. 明确解释图。

在当前漫画叙事生产基线中，第 7 项不能替代真实故事事件；若没有真实事件，应回到上游，而不是生成 PPT。

---

## 17. 连续性、稳定 ID 与可辨识性

重复出现的关键元素应有稳定身份：
- 角色；
- 因果道具；
- UI shell；
- 场景；
- 关键数量。

连续性既包括“是同一个东西”，也包括“观众一眼能认出来”。

必须保护：
- 人物身份和成熟度；
- 关键服装 / 轮廓；
- 道具几何与数量；
- 场景结构；
- UI shell；
- 时间 / 天气 / 昼夜；
- 回忆与原事件的状态一致性。

变化只改变故事事件实际改变的部分。

必须防止：
- 多肢体或影响叙事的解剖错误；
- 屏幕朝向与人物阅读关系不可能；
- 回忆与既定时间 / 天气 / 场景冲突；
- 因果物件存在但视觉上不可辨认。

这些约束必须在 Part 3 / Part 4 接口中明确表达。

---

## 18. 全集视觉多样性检查

全集视觉多样性不是只在最后才检查。

### 18.1 规划前检查

在整集 / 段落视觉策略阶段先确认：
- 主要段落的视觉载体是否已经区分；
- 人物行动 / 世界后果是否被已有 UI / reaction 轻易替代；
- Scene System 是否足以承载故事阶段；
- 重复是否有累积 / 调查 / 喜剧等明确用途；
- 是否已经出现“每个 complication 都只能再看一页屏幕”的趋势。

发现问题优先在逐 Beat 设计前解决。

### 18.2 Shotbook 完成后的验证

逐帧通过不代表整集通过。交给后续图片模块前，应连续查看整个 Shotboard，观察：
- 地点 / 功能区；
- 人物实际动作；
- 主要道具；
- POV；
- 屏幕是否承担必要意义；
- 真实世界后果是否出现；
- 主观 / 隐喻 / 一般示范是否保持正确事实属性。

重点检查：
- 长时间连续“坐桌前看手机”；
- 连续多个几乎相同 UI；
- 连续多个重复反应姿势；
- 每个 complication 都只通过另一张屏幕解释。

多样性不能靠：
- 无缘由换地点；
- 无缘由加配角；
- 无缘由换机位；
- 装饰背景。

应该优先让故事已经存在的不同 complication 呈现不同动作、发现、关系或现实后果。

同时检查故事递进：

> **相邻多个 Semantic Shot 是否只是在重复同一种困难、困惑、情绪或解释，而人物的处境、认知、关系、选择、策略和后果没有继续变化？**

视觉上换了地点、景别或构图，不等于故事已经推进；但不得为了制造递进而发明 Part 2 没有的事件。

---

## 19. 时间线字段

正式生产时间直接来自 Part 2.5 的最终配音音频与真实对齐 SRT；Part 3 不再用计划字速或字符数估正式时长，也不额外建立 Speech Unit 体系。

时间记录在 Visual Beat 中，并绑定：
- 正式 SRT cue / 文本范围；
- 实际开始 / 结束时间；
- 必要的真实停顿 / 静默窗口；
- 语义落点。

Part 3 可以决定：
- cut；
- hold；
- handoff；
- setup / reveal 切换；
- reaction 是否值得单独画；
- 一个口播范围由一张还是多张图承载；
- 哪些视觉锚点必须卡在特定语义位置。

Part 3 不可以：
- 发明每秒字数；
- 改 TTS speed；
- 改写正式 SRT 文本；
- 为了画面方便重新写口播；
- 把历史 2.7 秒 / 张当硬规则。

字幕结束、语音结束和后续静默窗口可以不同。Part 3 可以利用真实静默延续画面，但不能用字幕长度伪造新的语音时间。

如果视觉意义确实无法放入已有真实音频时间，返回 Part 2.5 / 上游重新判断：
`RETURN_TIMING_VISUAL_CONFLICT`。

长 hold 是人工复核信号，不是自动失败。

---

## 20. 100% 口播覆盖

最终锁定口播必须按原顺序在两层都可核对：

1. Semantic Shot 覆盖完整故事 / 口播范围；
2. Visual Beat 覆盖该 Shot 内全部正式 SRT cue / 必要语义落点。

难画的一句话可以共享已有画面，但不能静默删除。

一个 cue 可以由多张图分担视觉承接，多 cue 也可以共用一张图；这不代表重复播放或改写口播。

覆盖 QA 不能只检查“cue ID 都出现过”。还要确认：
- 文本顺序不变；
- 没有漏句；
- 没有同一段被错误重复归属；
- 多图承接同一 cue 时，各图承担的视觉意义清楚；
- 非口播标题、元数据、制作说明不计入覆盖。

如果漏掉实际口播：
`RETURN_SCRIPT_COVERAGE_GAP`。

---

## 21. 当前视觉风格边界

当前生产方向以已封存的两张画风参考图为准，整体强调：
> **温暖、简化、生活化的手绘叙事漫画感**

目标：
- 长期角色身份稳定；
- 同一单集内场景与关键物件保持连续，跨单集不固定长期场景；
- 一眼读懂主要故事信息；
- 适合大量静态图 / 有限动画生产；
- 单图精致度让位于跨图一致性、可读性与生产稳定性。

不是：
- 高细节独立插画；
- Q 版 / 幼态；
- 霓虹科技感；
- PPT / 信息图。

“简化画风”不等于“简化成人物幼态”。

三名长期角色与画风基线已在 Part 3 锁定；Part 4 负责具体 Beat 的参考图绑定、生成 / 编辑方式与图片执行。

---

## 22. 文本、UI 与可读事实

只有因果需要时才要求画面里出现可读文本。

当前规则：
- `TEXT_RENDER_MODE = NONE` 或 `IMAGE_NATIVE`；
- 不使用后期文字覆盖修复关键文本；
- 不使用 SVG / HTML / Canvas / PIL 文字；
- 不把错误文字后期“补正确”。

如果一个因果关键中文字符串必须可读，则后续成图必须逐字检查。

原生 UI 中自然存在的返回箭头、列表箭头等允许出现；禁止的是为了解释概念额外加的漂浮箭头。

Part 3 应只要求真正必要的文字，不把整集变成屏幕截图序列。

---

## 23. 与 Part 4 / Part 4.5 图片规划的边界

Part 3 最终应交付：
- 每个 Beat 为什么存在；
- 实际发生 / 显现的事件及事实属性；
- state_before / state_after；
- 最终静帧状态；
- 需要看谁 / 看什么；
- 景别；
- POV；
- POV reason；
- 构图与关注点；
- Scene / continuity 需要保持的逻辑锚点；
- 必要 withheld / reveal；
- 必要精确文字或允许集合；
- 可接受条件；
- 基于 Part 2.5 正式 SRT 的时间线锚点。

图片规划 Agent（Part 4 + Part 4.5）再决定：
- 查询哪些历史完整图片；
- 用哪张角色 / 场景 / 道具 / UI 参考；
- 直接复用 / 基于旧图修改 / 仅参考 / 新生成；
- source frame；
- prompt / edit instruction；
- 图片模型与执行依赖；
- 文件路径 / hash；
- 执行包 QA 与生产后素材候选。

生图执行 Agent只按已锁执行包执行，不重新导演、不重新查库、不改变复用决策。

当前下游生产约束必须保留：
- 每个 Beat 最终交付是一张完整图；
- `COMPOSITE_CROP = FORBIDDEN`；
- 不裁切拼装；
- 不外部图层拼贴；
- 不后期文字覆盖；
- DERIVE_EDIT 只适用于机位、主体、主要几何和身份兼容的状态变化；
- 机位 / POV / 主体集合 / 主要几何改变时应重新生成；
- 不设编辑比例或复用率配额。

Part 3 不替 Part 4 / Part 4.5 选择具体执行资产，但必须给出足够语义，保证图片规划 Agent 不需要自由猜故事意义。

---

## 24. 单主变化与复用边界

对连续状态 / 未来可编辑画面，尽量明确：
- 哪些元素必须保持；
- 这一张唯一主要变化是什么。

适合：
- setup → reveal；
- UI 状态变化；
- 同场景一个动作结果；
- before / after。

但“单主变化”是连续性工具，不是硬逼每张图只有一个差异。

如果新画面需要不同 POV、不同主体、不同主要空间结构，就不应伪装成原图的小改。

---

## 25. 图像 QA 反馈给导演的原则

后续成图 QA 应保护的是**故事意义**，不是每个像素级描述。

### 硬失败
- 观众读到错误事件；
- before / after 反了；
- 假设动作被画成已经完成；
- 关键数量 / 身份错；
- 多肢体 / 解剖错误影响故事；
- 视角物理不可能；
- 关键 UI 文字错误；
- 画面新增未批准事实；
- 回忆与已建立时空冲突；
- 抽象解释图替代真实事件；
- setup 提前泄露 reveal。

### 可记录的小偏差
在不改变事件、身份、因果、可读事实与连续性的前提下：
- 轻微景别差异；
- 无害设备外观小差异；
- 无害背景纹理；
- 不影响动作意义的手指距离；
- 不影响人物身份的轻微裁切。

不要为了修一个无意义的小细节反复付费重画。

---

## 26. Director 输出

正常生产输出：
1. 一份整集 / 段落视觉策略；
2. 一份 Semantic Shot → Visual Beat Shotbook；
3. 对应的人可读 Shotboard。

Shotbook 的机器可读结构统一为：
- `semantic_shots[]` 为唯一正式层级入口；
- 每个 Semantic Shot 的 `visual_beats[]` 直接包含完整 Visual Beat 对象；
- 不再额外维护重复的顶层 `visual_beats[]` 列表。

### 人可读 Shotboard 最少包含
- Semantic Shot ID；
- Beat ID；
- 正式时间（来自 Part 2.5 最终音频 / SRT）；
- 对应口播；
- 这一刻实际发生什么；
- 故事变化；
- 最终画面状态；
- 景别；
- POV；
- POV reason；
- 视觉意图；
- 主要焦点；
- state_before / state_after；
- relation / transition；
- continuity / reveal 备注；
- acceptance criteria。

它用于调试 / 审核，不要求每集再增加一个 Owner 强制审批环。

---

## 27. Part 3 QA

### 27.1 策略 QA：逐 Beat 设计前

- 主要段落的状态变化、主要视觉载体、人物行动 / 世界后果、UI职责是否已经明确？
- Scene System 是否说明地点 / 功能区的故事用途与重要状态？
- 重复出现的关键空间是否建立了 Scene Anchor，并明确延续与切换边界？
- 是否已经能预见长段手机 / UI / reaction 重复？
- 现实行动 / 空间 / 后果明明存在时，是否被更省事的 UI 替代？
- 是否为了丰富而准备无依据增加地点、配角、动作或机位？

策略 QA 不通过时先修改整集 / 段落视觉策略，不继续机械拆 Beat。

### 27.2 故事事件 / 事实属性

- 每个 Beat 是否有故事事件 / 状态，而不是解释旁白？
- 客观事件、已锁隐喻、主观脑补 / 假设、一般机制示范是否区分清楚？
- 主观脑补 / 假设 / 计划是否具有可执行且一眼可辨的视觉语法，而不是只写“主观气氛”？
- 是否新增了剧本没有的个案事实？
- hypothetical 是否仍然是 hypothetical？
- 一般示范是否被误画成本集具体因果证据？

### 27.3 Semantic Shot 递进

- 每个重要 Semantic Shot 结束时，是否能说清人物处境、认知、关系、选择、策略或重要后果发生了什么有意义变化？
- 是否把单纯的新信息 / 新表情 / 新机位误当成新的故事阶段？
- 相邻 Semantic Shot 是否在重复同一种困难、困惑、情绪或解释？
- 关键转折处，目标、阻力、预期与实际结果是否足够清楚？

### 27.4 Beat 经济性 / 最终状态

- 这张图是否新增动作、结果、关注点、因果状态或必要 POV？
- 最终静帧到底停在哪个状态？
- 是否把多步过程硬塞进一张图？
- 相邻画面能否由一张完整画面承载？
- 是否因为 SRT / 平均秒数而过度切图？
- setup / reaction 是否真的有意义？
- 若结论依赖 before / after，观众是否能从画面本身看出前后变化，而不是依赖解释标签？

### 27.5 POV / 单帧 / 连续性

- POV 是否有理由，摄像机、屏幕、人物目光是否物理成立？
- 第一眼能否看到主要故事任务？
- 是否有竞争焦点、背景抢戏或无意义文字？
- setup 是否泄露 reveal？
- 人物、道具、UI、场景、天气、时段、数量是否稳定？
- 已建立的 Scene Anchor 是否被后续 Shot / Beat 正确继承，且没有无理由切换空间或时段？
- 回忆与原事件是否一致？
- 因果物件是否足够可辨认？

### 27.6 全集验证

- 是否连续太多同地点、同手机、同构图？
- complication 是否呈现不同动作、发现、关系或后果？
- 多样性是否来自真实故事变化，而不是装饰？
- 已规划的 Scene System 与段落载体是否真正落实到 Shot / Beat？

### 27.7 覆盖与时间

- Semantic Shot 与 Visual Beat 两层是否 100% 覆盖最终口播？
- 文本顺序是否不变、没有漏项或错误重复？
- 时间是否来自 Part 2.5 最终音频 / 正式 SRT？
- 视觉意义是否能容纳在真实时间内？

### 27.8 与下游 QA 的责任归因

- **Part 3 原规划本身单调、场景系统 / 现实演绎不足、事实属性错误** → Part 3 修；
- **Part 3 正确，但 Part 4 + Part 4.5 编译成错误 / 过度相似的图片任务** → 图片规划 Agent 修；
- **执行包正确，但生成图片没有按任务实现** → 生图执行 Agent按 retry / fallback / HOLD 处理。

Part 3 不承担正常流程中的逐张最终成图验收，也不要求新增独立 Review Agent。
