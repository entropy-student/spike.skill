# Music Trend Radar（音乐趋势雷达）

> 跨平台音乐热榜 / 爆发歌曲识别 Skill。目标不是简单抄榜，而是回答：**今天哪些歌真的热、哪些正在爆、哪些只是单平台偏科。**

## 目标

从网易云音乐、QQ 音乐、汽水音乐的公开榜单/发现数据中建立音乐热度底盘，再加入 B 站二创传播信号，建立可核验的「今日音乐趋势雷达」。

核心输出分为：

1. **全民热歌**：多平台同时靠前，当前真实热度高。
2. **爆发中**：排名快速上升、跨平台同步进入，值得提前关注。
3. **新歌观察**：新歌榜强，但尚未转化为热歌榜强势。
4. **平台偏科**：在单一平台很强，但跨平台证据不足。
5. **稳定霸榜**：连续多日保持高位（需要历史快照）。
6. **趋势等级**：每首候选同时标记 B / A / S / S+，用于描述传播阶段，而不是替代榜单名次；S+ 进一步区分 `active / culture / legacy`。

本 Skill 默认只抓取榜单与歌曲元数据，不下载音乐音频。

### S+ 生命周期标签

- `S+ (active)`：当前音乐榜 + 社交/B站同时强爆发。
- `S+ (culture)`：音乐榜已回落，但最近 7 天挑战/手势舞/二创仍明显扩散。
- `S+ (legacy)`：当前不一定爆发，但已经沉淀为长期可复用的文化/BGM模板。

**Legacy 不能冒充今日热度**；它只描述文化地位。

---

## 核心原则

### 1. 榜单证据优先，搜索热度只能辅助

优先使用：

- 平台当前榜单结构化数据
- 平台公开页面
- 可验证的榜单 API / CLI

搜索引擎、社交讨论、新闻只能用于解释「为什么火」，**不能替代具体排名证据**。

### 2. 不要把「热门」和「正在爆发」混为一谈

- 热门：现在已经很靠前。
- 爆发：相较前一快照快速上升。
- 长红：连续多日稳定靠前。

如果没有历史快照，不得伪造涨跌、持续天数或“正在爆发”。

### 3. 不伪造汽水音乐“榜单”

若汽水只能获取发现页/推荐歌单，则必须写成：

> 汽水发现热度 / 推荐曝光

不能擅自称其为“热歌榜排名”。

### 4. 不从歌名猜 BPM / Key / 和声

「今日音乐 DNA」中的 BPM、调性、节奏、和声、能量曲线等，只有在获得可靠音频分析结果或可信元数据时才能输出。否则仅分析：

- 歌手/语言
- 新旧歌曲
- 版本类型
- 可验证的曲风标签
- 榜单结构趋势

## 数据源优先级

### 网易云音乐

首选：

- `NeteaseCloudMusicApiEnhanced/api-enhanced`
- `/toplist`
- `/toplist/detail`
- 通过榜单 ID 调用歌单详情

常用榜单：

- 热歌榜：`3778678`
- 新歌榜：`3779629`
- 飙升榜：`19723756`

若接口临时不可用，可使用网易云公开榜单页面作为替代；必须标记来源类型。

### QQ 音乐

首选：

- `tamnd/qqmusic-cli`
- `qqmusic top`
- `qqmusic top --chart new`
- `qqmusic top --chart rising`

该工具通过 QQ 音乐公开 toplist API 读取榜单数据，并支持 JSON/JSONL 输出。

### 汽水音乐

首选：

- `guowenye/qishui-api`
- `/discover`
- `/discover/mix`
- `/recommend/playlist`
- `/playlist/detail`

如果发现页能明确解析出平台命名的榜单块，则记录其榜单名称；否则只作为「发现热度」证据。

### B 站（二创传播层）

B 站不计入「音乐平台跨平台覆盖」数量，而作为独立 `Bili Breakout Score`：

- 搜索歌曲名 / 核心歌词 / 挑战名；
- 优先观察最近 7 天与最近 30 天的新投稿；
- 记录翻唱、舞蹈/手势舞、鬼畜、剧情 BGM、Remix、虚拟歌手、乐器演奏等衍生类型；
- 同一 UP 主批量搬运不能等同于多创作者扩散；
- 历史高播放只能证明「曾经热」，今日分数必须加入新投稿与近期互动证据。

B 站主要回答：**这首歌是否已经变成大家拿来继续创作的素材？**

---

## 抓取范围

默认每个平台抓：

- 热门/热歌 Top 100
- 飙升 Top 100（若平台提供）
- 新歌 Top 100（若平台提供）

第一次试跑可缩小到 Top 30，以降低抓取成本并方便人工核对。

## 标准化规则

统一记录：

```text
platform
chart
rank
song_id
title
artist
version
captured_at
source_type
source_url_or_ref
```

### 去重键

默认：

```text
normalized_title + normalized_primary_artist
```

处理规则：

- 去掉无意义空格、全半角差异。
- `Live` / `Remix` / `Acoustic` / `DJ版` 等明确版本默认保留为不同歌曲版本。
- 同一首歌不同平台 ID 需要合并成一个 canonical song。
- 同名不同歌手不得合并。

## 三种试跑模式

为了校准“准不准确”，初期固定并行输出三个版本。

### Run A：Current Heat（当前热度）

只看当前排名 + 跨平台重合。

适合回答：

> 今天大家最常听的歌有哪些？

### Run B：Breakout（爆发雷达）

看飙升榜 + 与上一次快照的排名变化。

适合回答：

> 哪些歌正在快速变热？

如果没有上一快照，只能输出「飙升榜候选」，不得声称实际涨幅。

### Run C：Balanced Radar（综合雷达）

综合：当前排名 + 跨平台覆盖 + 涨速 + 持续性。

这是最终推荐版本，但需要至少 2 次以上历史抓取才能发挥价值。

---

## 评分

详细公式见 `references/SCORING.md`。

原则：

> **排名决定“现在多热”，跨平台决定“是否破圈”，涨速决定“是否正在爆”，持续性决定“是不是长红”，Social Breakout 决定“有没有从歌曲变成传播模板”。**

默认不为三个音乐平台设置主观市场份额权重，三平台等权；B 站作为独立「二创传播层」计分，不冒充音乐榜单平台。后续只有在有可靠市场数据时才调整。

---

### 趋势等级：S+ / S / A / B

详细门槛见 `references/TIERING.md`。

- **B**：已有真实热度，但主要仍是单平台或早期信号。
- **A**：强势热门 / 明显爆发，开始跨平台扩散。
- **S**：多平台强势并完成明显破圈。
- **S+**：现象级歌曲，已经出现手势舞、挑战、翻唱、BGM 模板、梗化二创等可复制传播。

等级和综合名次允许不一致。例如某歌音乐榜只能排 #15，但短视频挑战正在爆发，可以是 A；反之单平台 #1 也不自动等于 S。

S/S+ 不允许只靠一个分数自动判定；必须满足跨平台和证据门槛。历史不足时使用 `S候选` / `S+候选`。

## 置信度

每首歌必须给出 Confidence：High / Medium / Low。

### High

- 至少 2 个平台有直接榜单证据；或
- 单平台官方/直接 API 排名 + 历史快照完整。

### Medium

- 只有 1 个平台的直接榜单证据；或
- 汽水为明确发现页/推荐块，但不是正式榜单。

### Low

- 主要依赖搜索结果、转载榜单或非当天数据。

Low 结果不得进入 Top 5，除非明确标注“观察项”。

---

## 反幻觉 / 失败规则

1. 抓不到某个平台：写「本轮未取得可靠数据」，不要补猜。
2. 榜单日期不明确或超过 24 小时：不得作为“今日排名”。
3. 没有上一快照：不输出具体“上升 X 位”。
4. 只有单平台出现：不得叫“跨平台爆款”。
5. 无可靠音频分析：不得输出 BPM、Key、和声、能量曲线等精确音乐学参数。
6. 同一歌曲多版本：先标准化，再决定是否合并；不得直接按歌名粗暴去重。

## 工作流程

### Step 1：确定时间窗口

默认使用用户当前本地日期，抓取「今日/最近一次更新」榜单。

### Step 2：网易云

抓热歌 / 飙升 / 新歌。

### Step 3：QQ 音乐

抓热歌 / 飙升 / 新歌。

### Step 4：汽水音乐

优先寻找官方命名榜单块；否则抓发现页/推荐歌单，并降级标记。

### Step 5：B 站二创信号

抓取/检索最近 7 天和 30 天的歌曲相关投稿，计算 `Bili Breakout Score`，并记录二创类型多样性与最近一次活跃时间。

### Step 6：标准化与跨平台合并

对标题、歌手、版本做 canonicalization。

### Step 7：输出 Run A / B / C

初期校准时三个版本都输出 Top 10，方便人工比较。

### Step 8：补充 Social Breakout

检查短视频/社交平台是否出现：手势舞、舞蹈挑战、固定 BGM、翻唱、Remix、明星参与、集中二创。

Social 只能使用可验证传播证据；搜索/新闻只能补充解释。

### Step 9：判定 S+/S/A/B

同时输出 `Rank + Tier + Confidence`。名次和等级不得互相替代。

### Step 10：给出“为什么”

解释依据必须是：

- 当前排名
- 跨平台出现
- 飙升榜出现
- 历史涨跌
- 连续上榜

不要使用空泛的“最近很火”。

### Step 11：记录校准反馈

用户可对每首歌标记：

- 准
- 一般
- 不准
- 我在平台里没看到这么热

把反馈写入 calibration log，下一版调整权重和源可靠性。

### 今日结论

一句话说明今天是「头部集中 / 多首爆发 / 新歌换挡 / 平台分化」中的哪一种。

### Run A — 当前最热

| # | 歌曲 | 歌手 | 网易云 | QQ | 汽水 | B站 | Heat | Tier | Confidence |
|---|---|---|---:|---:|---:|---:|---:|---|---|

### Run B — 正在爆发

| # | 歌曲 | 依据 | 涨势 | Tier | Confidence |
|---|---|---|---|---|---|

### Run C — 综合雷达

| # | 歌曲 | 类型 | 综合分 | Tier | 为什么值得看 |
|---|---|---|---:|---|---|

### 平台差异

总结网易云 / QQ / 汽水的音乐平台差异，并单列 B 站最强二创歌曲与衍生形式。

### 数据缺口

明确列出本轮没有可靠取得的数据。

## 校准期的推荐调用

> 调用 Music Trend Radar，抓今天网易云、QQ 音乐、汽水音乐的热歌/飙升/新歌数据，同时加入 B 站最近 7 天/30 天的二创传播证据。先按校准模式输出 Run A 当前热度、Run B 爆发雷达、Run C 综合雷达三个 Top 10，并输出 S+/S/A/B。音乐平台排名必须来自当天可验证数据；B 站只作为二创传播维度，不能冒充音乐榜单。抓不到的平台明确缺失，不要猜。第一次运行没有历史快照时，不要伪造涨跌。

## 未来升级

当外部 `trend-radar` 项目就绪后，本 Skill 只负责：

- 调用采集器
- 解释评分
- 输出报告
- 结合用户目标进行选歌 / 创作趋势分析

历史数据、定时抓取、数据库与长期涨跌计算应交给项目层，而不是让 Skill 自己假装拥有持久状态。
