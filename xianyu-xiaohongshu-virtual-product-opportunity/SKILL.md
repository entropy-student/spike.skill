# 闲鱼 / 小红书虚拟商品选品 v2.0

## 1. 默认目标

默认只回答：

> **平台上哪些具体商品类型 / SKU / Offer 有真实需求？**

默认终点是**证据可复核的商品目录**，不是强行选冠军，也不要求找货源、上架或真实成交测试。

只有用户明确提出“最推荐哪个”“哪个值得卖”“下一步真实测试”时，才启用第 8 节的 **Test Mode**。

## 2. 三条总原则

1. **平台优先，而不是能力优先**
   - 先看平台原生类目、当前商品、交易结构。
   - “我们会做什么”“某服务能否产品化”只能补充候选，不能主导市场结论。

2. **Transaction > Intent > Attention**
   - 真实订单/平台交易数据 > 明确购买动作/有效询盘 > 搜索/想要/收藏 > 浏览/点赞/曝光。
   - 卖家累计“卖出 X 件”不得冒充某个 SKU 销量。

3. **需求与执行分开**
   - 暂时找不到货源、授权、交付方案，不等于没有需求。
   - 明显违规/盗版/破解/作弊/绕审核等可以记录为市场信号，但标为 `MARKET_SIGNAL_ONLY`，不当作干净可执行商品推荐。

## 3. 每次调用先确定范围

从用户当前请求直接确定：

- `PLATFORM`: XIANYU / XHS / DUAL
- `SCOPE`: 虚拟商品 / 数字产品 / 服务产品化 / OPEN
- `MODE`: 默认 `MARKET_MAP`；用户明确要求实际选择时才用 `TEST`

只在缺失信息会显著改变结果时提问；否则用 `OPEN` / `UNKNOWN` 继续，不要为了流程而提问。

双平台必须分别判断，不能拿闲鱼成交证明小红书成立，反之亦然。

正式 Run 默认使用**当前市场信息**。如果商品形态明显涉及平台规则、类目资格或知识产权风险，核对当前官方规则；在 `MARKET_MAP` 中规则用于标记风险/`MARKET_SIGNAL_ONLY`，不用于抹掉已经观察到的市场需求。

## 4. Discovery：先扫真实市场

正式研究按这个顺序：

~~~text
1. 官方平台类目 / 市场面
2. 当前直接商品 / SKU / Offer
3. 平台或第一方交易数据
4. 多卖家 / 多商品重复出现
5. 搜索意图、问题与评论
6. 服务转产品化 / Workflow / 能力相邻，只作补充
~~~

### 闲鱼

优先看：
- 官方类目和当前商品；
- 价格、想要、浏览、直接购买结构；
- 同类商品是否由多个独立卖家持续出现；
- 标题关键词是否代表明确即时需求。

### 小红书

优先看：
- 搜索结果中的重复问题和商品/服务 Offer；
- 店铺/商品动作、合格私信或明确求购；
- 多个独立账号是否围绕同一需求持续出现；
- 收藏/点赞只算注意力，不算付款。

不要固定从某几个旧品类出发。每次都允许市场出现新的商品面。

## 5. 证据怎么记

每个候选至少记录：

~~~text
商品类型 / SKU
标准搜索词
平台
当前价格或价格带
证据来源
Provenance
需求等级
持续性 / 季节性
主要反方证据
Confidence
Status
~~~

### Provenance

- `PLATFORM_TRANSACTION`：平台/第一方交易数据直接点名该商品族。
- `PLATFORM_CATEGORY`：平台官方类目证明这个市场面存在。
- `DIRECT_SKU`：当前直接观察到对应商品。
- `RELATED_RESULTS_CLUSTER`：多个当前相关/推荐商品形成一致商品簇。
- `DERIVED_ADJACENT`：从相邻需求推导出的候选。

### 需求等级

- **D4**：平台/第一方交易级商品族证据，或可明确归属的 SKU 成交证据。
- **D3**：多个独立当前平台商品/卖家重复证明。
- **D2**：一个直接当前 SKU，或一个一致的当前商品簇。
- **D1**：只有官方类目、宏观数据或相邻需求。
- **U**：证据不足。

一个商品“想要”很高可以增强 D2，但**不能单凭一个商品变成 D3/D4**。

同一卖家矩阵、同一推荐链、同一热点转载链必须去重。

证据不足时不要平均补所有字段；优先补**最可能改变 D-Level / Status 的关键 UNKNOWN**。

## 6. SKU 粒度

输出必须足够具体，可以直接拿去搜索。

太宽：
- 软件
- 教程
- 教育资料
- 摄影素材

合理：
- AI 漫剧制作教程 + 项目文件 / 工作流
- 院校/专业考研复试资料包
- 日系胶片 Lightroom / PS 人像预设
- WordPress 外贸站主题模板包
- 迅雷 SVIP 月卡/周卡

如果一个候选只是从相邻市场推导出来，保留 `DERIVED_ADJACENT`，不要假装已经证明。

## 7. 默认输出：Market Map

最终状态只用四类：

- `CONFIRMED_DEMAND`：D4 或强 D3。
- `PROBABLE_DEMAND`：D3，或有较强佐证的 D2。
- `WATCHLIST`：D2/D1，但证据还不够强。
- `MARKET_SIGNAL_ONLY`：需求可见，但观察到的商品形态存在明显违规/侵权/账号或规避风险。

不强制 Top 3 / Top 10 / 唯一冠军。数量由证据决定。

标准输出表：

| 商品类型 / SKU | 搜索词 | 平台 | 价格带 | Provenance | 需求等级 | 当前证据 | 持续性 | 反方证据 | Confidence | Status |
|---|---|---|---:|---|---|---|---|---|---|---|

如果用户只要简短答案，可以只展示高置信度部分，但研究底稿仍应保留弱证据与 UNKNOWN。

## 8. 可选 Test Mode

**只有用户明确要求“哪个最值得卖/测试/优先做”时启用。**

先从 Market Map 中取证据最强的一小组，再补：

1. 当前平台规则 / 类目资格；
2. 免费替代与差异化；
3. 竞争与价格压缩；
4. 信任 / Proof；
5. 经济性：价格、人工、退款、维护；
6. 交付 / 隐私 / 版权 / 争议；
7. 与本次明确给出的操盘资源是否匹配；
8. Counterevidence：什么新证据会直接推翻它。

此时才允许输出：

~~~text
PRIORITY TEST
BACKUP
HOLD
KILL
NO PICK
~~~

以及最小真实验证方案。

Test Mode 的详细检查见 `references/OPTIONAL_TEST_MODE.md`。

## 9. 禁止误读

- 卖家多 ≠ 买家多。
- “想要”/收藏 ≠ 订单。
- 浏览/点赞 ≠ 付款。
- 推荐页 ≠ 搜索深度或市场份额。
- 同一卖家的多条商品 ≠ 多份独立证据。
- 一个爆款 SKU ≠ 整个品类都强。
- 平台 A 的证据 ≠ 平台 B 的证据。
- 相邻需求 ≠ 具体 SKU 已被验证。
- 暂时没有货源 ≠ 没有需求。
- 观察到别人违规卖 ≠ 平台允许。
- 数据不足就写 `UNKNOWN`，不要补数字。
